# 机械革命控制中心「电源设置」模块逆向分析与移植方案

> 分析对象：ControlCenter 5.56.60.34（Mechrevo GX 定制版，`CustomizeTarget = 56`）
> 分析方法：UI 层静态反编译 + 服务端元数据/常量取证 + 配套组件提取 + 本机运行时实测（注册表 / WMI / PnP / powercfg / UIA）
> 分析日期：2026-11-02　｜　目标机型：MRID6（Ryzen 7 7745HX + RTX 4060）

---

## 0. 结论速览

1. 「电源」页在程序内部是 `PowerManagePage` + `PowerManageViewModel`（导航项 `电源`，索引 4）。UI 自身**不做任何电源控制**，只把点击翻译成 MQTT 动作字符串发往 `Setting/Control` 与 `BatteryProtection/Control`。
2. 该页共 **8 个可配置项**（3 个在本机可见、5 个被能力位隐藏）+ 1 个只读电池信息面板 + 1 个无 UI 的后台电量校正任务。
3. 服务端把 8 项分流到 **五条互不相同的技术通道**：ACPI-EC 直读（`\\.\ACPIDriver`，GPD IOCTL）、电池类驱动 IOCTL（`IOCTL_BATTERY_*`）、`powrprof.dll` 电源计划 API、注册表 `HKLM\SOFTWARE\OEM\GamingCenter2\*`、以及重启/命令行副作用。
4. 本机（MRID6）实测：**官方 ACPI 驱动未安装、设备 `ACPI\INOU0000` 不存在**，`\\.\ACPIDriver` 打开失败；唯一固件通道是 `root\WMI:MICommonInterface`（MIFS），其功能号只到 **fn23**，**不含任何充电阈值/开关项**。
5. 因此本机的现实是：**「高性能电源模式」真生效（切电源计划），「电池健康保护三档」「关机 USB 供电」「深度睡眠」「来电自启」「电池 Logo」全是状态记忆（假开关）**。取证：UI 当前选中「工作站模式」，而电池实测 **99% 且已接电**——若阈值真生效应停在 60% 附近。
6. 移植建议按 **P0（真机可实现）/ P1（需协议逆向）/ P2（不建议）** 三级推进：P0 补电池信息与电源模式；P1 攻 EC 充电阈值；P2 是 OSD/Logo 这类本机固件不支持的项。

## 2. 总体架构

```
┌────────────────────────────────────────────┐
│ CCUWinUI.exe (MSIX/AppContainer)           │
│  PowerManagePage + PowerManageViewModel    │
│  仅做：UI 绑定 / 能力位门控 / 字符串拼装    │
└──────────────┬─────────────────────────────┘
               │ MQTT 127.0.0.1:13688
   publish ────┤ Setting/Control          {"Action":"USB_CHARGER_ON"}
               │ BatteryProtection/Control {"Action":"HEALTHYMODE"} / {"Report":"GET"}
   subscribe ──┤ System/BatteryProtection  {HealthProtectionStatus, BatteryPercent, ...}
               │ Setting/Status            {UsbCharger, HighPerformancePowerModeSwitch, DeepSleep...}
┌──────────────▼─────────────────────────────┐
│ 后台服务（官方 GCUService / 本机 JiaoLongCCUBridge）│
└───┬──────────┬───────────┬──────────┬───────┘
    │          │           │          │
  ACPI-EC   电池类驱动   powrprof   注册表 + 命令行
  (\\.\ACPIDriver  IOCTL  电源计划    MySetting / DeepSleep
   GPD IOCTL)  BATTERY_*  overlay     + shutdown /r
```

### 2.1 主题与职责

| 主题 | 方向 | 内容 |
|---|---|---|
| `Setting/Control` | UI → 服务 | `USB_CHARGER_ON/OFF`、`ACRECOVERY_TOGGLE_*`、`HIGHPERFORMANCEPOWERMODE_*`、`BATTERYLOGO_TOGGLE_*`、`DEEPSLEEP_ON/OFF`(带 `Secs`)、`PowerLight_ON/OFF/Brightness`、`GETSTATUS` |
| `BatteryProtection/Control` | UI → 服务 | `{Report:"GET"}` 拉全量电池状态；`PERFORMANCEDMODE` / `BALANCEDMODE` / `HEALTHYMODE` 切档 |
| `System/BatteryProtection` | 服务 → UI | `HealthProtectionStatus`、`BatteryPercent`、`BatteryTime`、`BatteryFullTime`、`BatteryPowerStatus`、`BatteryAbnormal`、Type-C 两项 |
| `Setting/Status` | 服务 → UI | `UsbCharger`、`HighPerformancePowerModeSwitch`、`DeepSleepSwitch`、`DeepSleepTime`、`AcRecoverySwitch_Support/_Status`、`BatteryLogo_Status`、`PowerLightSwitch/Brightness` |

### 2.2 UI 侧唯一出入口

`PowerManageViewModel.PowerSwitching(name)` 是开关类动作的唯一出口（纯字符串拼装）；`SetBatteryMode(mode)` 是档位类的出口；`InitializePowerInfo()` 在 `OnNavigatedTo` 里发两条拉取请求：

```csharp
// 进页面就拉全量
SendTopic("BatteryProtection/Control", new { Report = "GET" });
SendTopic("Setting/Control",            new { Action = "GETSTATUS" });
```

**关键设计**：UI **从不检查操作是否成功**，只等服务端回发的状态主题刷新开关。服务端未实现的动作在界面上表现为「点了保持不动」而不报错——这正是本机假开关不会暴露的原因。

## 4. 逐项逆向

### 4.1 电池健康保护三档（核心，唯一"改硬件"的电池项）

**界面语义**（UI 原文）：

| 档位 | 文案 | 预期效果 |
|---|---|---|
| PerformanceMode | 长效模式：提供最长的电池续航力 | 充满 100% |
| BalancedMode | 均衡模式：通过限制电池充至满电的电量，在续航力略微缩短的情况下，有效延长电池寿命 | 约 80% |
| HealthyMode | 工作站模式：进一步缩短电池续航时间，以换取电池寿命的最大延长，强烈建议长时间连接电源用户选用 | 约 60% |

**动作**：`BatteryProtection/Control {"Action":"PERFORMANCEDMODE|BALANCEDMODE|HEALTHYMODE"}`

**服务端实现**（`GCUService.MySystem.BatteryProtection2`）**[直证 + 推证]**：

```csharp
private enum Battery_Commands {
    GET, CHARGING_UP_LIMIT, CHARGING_DOWN_LIMIT, RECOVERY,
    TYPE_C_ADAPTOR_PRIORITY_SWITCH_ON, TYPE_C_ADAPTOR_PRIORITY_SWITCH_OFF
}
private enum BatteryHealthProtection_Status { PERFORMANCEDMODE, BALANCEDMODE, HEALTHYMODE }

private MyEcCtrl EcCtrl;                      // ACPI-EC 直读通道
private PowerPlanSetting PowerPlanSet;
private int m_BatteryChargingLimit_Up_Default;    // 出厂上限（从 EC 读回）
private int m_BatteryChargingLimit_Down_Default;
private int m_HealthProtectionStatus;
private void SetBatteryChargingLimit_Up(int limit);
private int  ReadBatteryChargingLimit_Up();
private void SetBatteryChargingLimit_Down(int limit);
private int  ReadBatteryChargingLimit_Down();
private void SetHealthProtectionHigh() / Middle() / Low();
```

对应 EC 寄存器 **[直证：`Define/ECSpec.cs`]**：

| 常量 | 地址（十进制 / 十六进制） | 含义 |
|---|---|---|
| `ADDR_BATTERY_CHARGE_LIMIT_UP` | 1977 / **0x7B9** | 充电上限（%） |
| `ADDR_BATTERY_CHARGE_LIMIT_DOWN` | 2000 / **0x7D0** | 充电下限 / 恢复充电阈值（%） |
| `ADDR_BATTERY_ALERT_BYTE` | 1172 / 0x494 | 电池告警 |
| `ecBt1RSOC` | 1195 / 0x4AB | 相对电量 |
| `ADDR_EC_BT1CycleCount_BYTE1/2` | 1190/1191 / 0x4A6-0x4A7 | 循环次数 |
| `ADDR_EC_BIF_DC_BYTE1/2` | 1026/1027 / 0x402-0x403 | 设计容量 |
| `ADDR_EC_BIF_DV_BYTE1/2` | 1032/1033 / 0x408-0x409 | 设计电压 |
| `ADDR_EC_BST_BRC_BYTE1/2` | 1078/1079 / 0x436-0x437 | 剩余容量 |
| `ADDR_EC_BST_BPV_BYTE1/2` | 1080/1081 / 0x438-0x439 | 当前电压 |
| `ADDR_COMPLEX_POWER_STATUS` | 1996 / 0x7CC | 复合电源状态 |
| `ADDR_AP_MISCSWITCH2` | 3407 / 0xD4F | 杂项开关 2 |

**写入序列 [推证]**：`SetHealthProtectionHigh/Middle/Low` → `SetBatteryChargingLimit_Up(n)` + `SetBatteryChargingLimit_Down(m)` → `SetRegistry()` 落盘 → `SendToUI()` 回 `System/BatteryProtection`。三档的具体数值由 `m_BatteryChargingLimit_*_Default`（EC 出厂值）推导，方法体已清空，**无法静态读出确切百分比**；按 UI 文案与业界惯例应落在 100 / 80 / 60 三档。

**旧版 `BatteryProtection`（非 2）还在做另一件事**：字段 `PowerCorrectionMin/Max`、`CorrenctionSTAGE1-3`、`CorrectionTime(int days)`、`AutoCorrection()` —— 这是**电池电量校正/标定**（满充满放校准 RSOC），由服务端定时器自动触发，**UI 无入口**。属隐藏功能。

**注册表**：`HKLM\SOFTWARE\OEM\GamingCenter2\BatteryProtection`（`ProtectionSwitch`、`CorrectionSwitch`、`NotificationSwitch`、各 STAGE 状态、`FinishDateTime`）。

### 4.2 高性能电源模式

**界面**：`ToggleSwitch HighPerformancePowerMode`，文案「在合适的场景下自动运用高性能电源模式。」

**门控**：`RefreshItemsSupport()` 里 `HighPerformancePowerModeSupport = !Convert.ToBoolean(registryValue)`——**取值取反**，本机 `=0` 反而**显示**。这是官方的一个语义坑（键名写的是"支持"，实际当"禁用"用）。

**动作**：`HIGHPERFORMANCEPOWERMODE_ON/OFF` → `MySettingManager.UserSetHighPerformancePowerMode(status)` → `PowerPlanSetting.HighPerformanceActive()` / `BalanceActive()`。

**底层 [直证]**：`MyControlCenter/PowerOptionAPI.cs` 封装了完整的 `powrprof.dll` 电源计划 API：

```csharp
PowerEnumerate / PowerReadFriendlyName / PowerDuplicateScheme / PowerWriteFriendlyName
PowerImportPowerScheme / PowerDeleteScheme / PowerRestoreDefaultPowerSchemes
PowerGetActiveScheme / PowerSetActiveScheme
PowerRead/WriteACValueIndex / PowerRead/WriteDCValueIndex   // 子组 + 设置 GUID 粒度
PowerSetActiveOverlayScheme(Guid)                            // Win10 1709+ 电源模式覆盖
private Guid m_guid_Gaming;                                  // 自建"游戏"计划
powerWriteHiPerformanceName / powerWriteGamingModeName / powerWriteBalancedName / powerWritePowerSavingName
```

**语义**：这是**整套电源计划的创建/改名/激活**，不是单一开关。官方会 `PowerDuplicateScheme` 复制平衡计划 → `PowerWriteFriendlyName` 改成品牌名 → `PowerSetActiveScheme` 激活；`PowerSetActiveOverlayScheme` 用于 Win11 的"电源模式"覆盖层（节能/平衡/最佳性能）。`POWER_PLAN_GAMING` / `POWER_PLAN_POWERSAVING` 等动作在本页未使用，但 `ServCMD.MySetting` 里仍保留（旧版 UI 的 4 档入口）。

**本机现状**：`powercfg /list` 只有「平衡」「高性能」两个计划，当前激活 `8c5e7fda-…`（高性能）。桥接直接 `PowerSetActiveScheme(系统内置高性能 GUID)`，**没有** 官方那套"复制+改名"的品牌计划。功能等价、观感不同。

### 4.3 关机下使用 USB 给电

**界面**：`ToggleSwitch USB`，文案「可在关机或休眠状态下支持 USB 给电，但不支持所有手机机型充电。」

**动作**：`USB_CHARGER_ON/OFF`，回读 `MySetting.UsbCharger` 与 `USB_CHARGER_STATUS_ON/OFF`。

**底层 [直证]**：`ECSpec.TriggerByteFlag`

```csharp
public enum TriggerByteFlag {
    WinLock_Trigger = 1, LightBar_Trigger = 2, FanBoost_Trigger = 4, SilentMode_Trigger = 8,
    USBCharger_Trigger = 0x10,
    RGBKeybaord_Trigger = 0x20, RGBLogo_Trigger = 0x40, RGBKeybaordWelcome_Trigger = 0x80,
    E_Shutter_Trigger_Camera_Off = 0,
    E_Shutter_Trigger_Camera_On  = USBCharger_Trigger   // ← 复用同一位！
}
public const ushort ADDR_TRIGGER_BYTE  = 1895;  // 0x767
public const ushort ADDR_TRIGGER_BYTE2 = 1885;  // 0x75D
```

即**写 EC 触发字节的第 4 位（0x10）**。注意 `E_Shutter_Trigger_Camera_On` 与 `USBCharger_Trigger` 同值：摄像头电子快门与 USB 充电在不同项目上复用同一触发位，靠项目 ID 区分语义——这是移植时必须小心的"一写两义"。

**语义**：关机/休眠后 USB 口继续供电（关机充电）。属于 EC 直接控制，与 BIOS 里 "USB PowerShare / Always On USB" 是同一功能的两个入口。

### 4.4 深度睡眠（本机隐藏）

**界面**：`ToggleSwitch DeepSleep` + `ComboBox`（900 / 1200 / 1500 / 1800 秒四档）。

**门控**：`APVersionCheck >= 24`。本机 `= 0` → 隐藏。

**动作**：`DEEPSLEEP_ON {"Secs": 900|1200|1500|1800}` / `DEEPSLEEP_OFF`；切换后 UI **强制弹重启对话框**，确认时先发 `DEEPSLEEP_ON`，`Thread.Sleep(500)`，再发 `DGPU_DIRECT_CONNECT_RESTART`（`shutdown /r`）——说明该设置**必须重启才生效**。

**注册表 [直证]**：`HKLM\SOFTWARE\OEM\GamingCenter2\MySetting\DeepSleep`（`DeepSleepStatus`、`DeepSleepTime`）。UI 在服务端未回该字段时会**直接读这个注册表兜底**：

```csharp
RegistryKey.OpenBaseKey(RegistryHive.LocalMachine, RegistryView.Registry64)
    .OpenSubKey("SOFTWARE\\OEM\\GamingCenter2\\MySetting\\DeepSleep")?.GetValue("DeepSleepStatus");
```

**服务端 [推证]**：`MySettingManager.SetDeepSleepTime(bool enable, int seconds)` 是 `async` 方法，同类里配套 `RunCmd(string cmd)` / `ExecuteCommand(string command)` → 落地方式大概率是**写 EC + 调命令行**（`powercfg` 或 `reg`）的组合；方法体已清空，无法确认是否纯注册表。

**语义**：BIOS 级"深度睡眠/深度待机"超时——空闲 N 秒后进入更深的省电态（EC 断电域更大）。与 Windows 的"睡眠/休眠"不是一回事。

### 4.5 来电自启

**界面**：`ToggleSwitch AcRecovery`。门控 `AcRecoverySwitchSupport != 0`（本机 0 → 隐藏），且 `customizeTarget ∈ {11, 27}` 时强制关闭。

**动作**：`ACRECOVERY_TOGGLE_ON/OFF` → `MySettingManager.UserSetAcRecoverySwitch(int status)`。

**底层 [推断]**：无独立设备通道常量，实现应为 **EC/BIOS 位**（`ADDR_AP_OEM_BYTE` 系列未在反编译产物中与该方法显式绑定）。语义 = 掉电恢复后重新接上市电时自动开机（BIOS 的 "AC Recovery / Restore on AC Power Loss"）。

### 4.7 电源指示灯亮度

**界面**：`ToggleSwitch PowerLightAdjustSupportSwitch` + `OCSlider PowerLightSlider`（0-100，`PowerLightSliderState` 视觉状态控制滑块显隐）。

**门控**：`APVersionCheck >= 25 && BIOS_PROJECT_ID ∈ {IDP, ID2}`。本机 `ID6` + `0` → 隐藏。

**动作**：`PowerLight_ON/OFF`（带 `Brightness`）、`PowerLight_Brightness {"Brightness": n}`。

**底层 [直证]**：`ECSpec.PowerLight_LEDPWM = 2040`（0x7F8）。方法 `InitPowerLightEC(bool switchStatus, int value)` / `UserSetPowerLight(bool, int)` —— 开关与亮度是两个独立写入。

### 4.8 Type-C 适配器优先级（本机不支持）

**界面**：两个 `RadioButton`（充电优先 / 性能优先），文案「Type-C 充电优先级」。

**门控**：服务端回 `TypeCAdaptorPrioritySupport`；本机桥接固定 `false` → 隐藏。

**服务端 [直证]**：`BatteryProtection2.Battery_Commands.TYPE_C_ADAPTOR_PRIORITY_SWITCH_ON/OFF`，字段 `m_TypeCAdaptorPrioritySwitch` / `m_TypeCAdaptorPrioritySupport`，支持位来自 `MyEcCtrl.GetTypeCAdaptorPrioritySupport()`（读 EC 特性位）。

**语义**：接 Type-C PD 电源时，优先给电池充电（充电优先）还是优先保证系统功耗（性能优先，可能降充电功率甚至不充）。与 4.1 的 `CHARGING_UP/DOWN_LIMIT` 是两套机制。

### 4.9 电池信息面板（只读，但采集路径很关键）

**官方采集 [直证：`BatteryModel/Win32.cs` + `BM_Manager`]**：**不用 WMI，直接走电池类驱动 IOCTL**：

```csharp
GUID_DEVCLASS_BATTERY + SetupDiGetClassDevs / SetupDiEnumDeviceInterfaces
CreateFile(devicePath)
IOCTL_BATTERY_QUERY_TAG         = 2703424  (0x294340)
IOCTL_BATTERY_QUERY_INFORMATION = 2703428  (0x294344)   // BATTERY_INFORMATION 级别
IOCTL_BATTERY_QUERY_STATUS      = 2703436  (0x29434C)

struct BATTERY_INFORMATION { Capabilities; Technology; Chemistry[4];
                             DesignedCapacity; FullChargedCapacity;
                             DefaultAlert1/2; CriticalBias; CycleCount; }
struct BATTERY_STATUS      { PowerState; Capacity; Voltage; Rate; }
```

`BM_Manager` 的五个 Getter 与之严格对应：`GetBatteryLife`（百分比）、`GetCurrentCapacity`、`GetRate`（放电率）、`GetDesignCapacity`、`GetFullCapacity`、`GetVoltage`。

**为什么重要**：本机 `root\wmi` 里 **`BatteryStaticData` 类不存在**（拿不到 `DesignedCapacity`），但 IOCTL 通道能拿到全部字段，包括设计容量与 `Rate`。移植若要显示"设计容量 / 损耗率 / 当前功率"，**必须走 IOCTL 而不是 WMI**。

**UI 格式化逻辑 [直证]**：

| 字段 | 规则 |
|---|---|
| `BatteryPercent` | 0-100；≤20 红 `(200,255,0,0)`、≤40 橙 `(200,255,169,0)`、>40 绿 `(200,0,255,0)` |
| `BatteryTime` | 秒 → 分钟；`-1` 显示 `" ---"` |
| `BatteryFullTime` | 秒 → `h 小时 m 分钟`；`-1` 显示 `" ---"` |
| `BatteryPowerStatus` | `"1"` = 接电/充满，驱动「已连接电源适配器」与充电图标 |
| `BatteryAbnormal` | 0 正常；1 系统无电池；2 电池老化；3 充电异常 |

## 8. 移植方案

### 8.1 范围分级

| 级别 | 内容 | 理由 |
|---|---|---|
| **P0（建议立即做）** | ① 电池信息面板真实化（IOCTL 直读）② 高性能电源模式补齐 overlay 与计划管理 ③ 深度睡眠映射到 `HIBERNATEIDLE` | 零固件风险，全部走 Windows 公开 API，收益立竿见影 |
| **P1（需先做协议验证）** | ④ 电池三档充电阈值（EC 0x7B9/0x7D0）⑤ 关机 USB 给电（EC 0x767 bit4） | 依赖 EC 访问通道，需先解决"怎么安全读写 EC" |
| **P2（不建议投入）** | ⑥ 来电自启 ⑦ 电池 Logo ⑧ 电源指示灯 ⑨ Type-C 优先级 | 本机能力位为 0 / 硬件不支持 / 无 UI 入口，做了也看不见 |

### 8.2 实现思路

#### P0-① 电池信息面板真实化

参照 `BatteryModel/Win32.cs` 的 IOCTL 方案重写桥接的 `SendBatteryStatusAsync()`：

```csharp
// 1) 枚举电池设备接口
SetupDiGetClassDevs(GUID_DEVCLASS_BATTERY, null, IntPtr.Zero, DIGCF_PRESENT|DIGCF_DEVICEINTERFACE)
SetupDiEnumDeviceInterfaces / SetupDiGetDeviceInterfaceDetail
// 2) 打开并查询
handle = CreateFile(path, GENERIC_READ|WRITE, FILE_SHARE_READ|WRITE, ...)
DeviceIoControl(handle, 0x294340 /*QUERY_TAG*/,   null, 0, ref tag, 4, out _, null)
DeviceIoControl(handle, 0x294344 /*QUERY_INFO*/,  ref query, size, ref info, size, out _, null)  // BatteryInformation
DeviceIoControl(handle, 0x29434C /*QUERY_STATUS*/,null, 0, ref status, size, out _, null)
```

映射到 UI 字段：

| UI 字段 | 数据源 |
|---|---|
| `BatteryPercent` | `BATTERY_STATUS.Capacity * 100 / BATTERY_INFORMATION.FullChargedCapacity`（或 `ecBt1RSOC`） |
| `BatteryFullTime` | `(FullChargedCapacity - Capacity) / ChargeRate * 3600`；`Rate<=0` 时给 `-1` |
| `BatteryTime` | `Capacity / |Rate| * 3600`；放电率 0 时给 `-1` |
| 设计容量 / 满充容量 / 健康度 | `DesignedCapacity` / `FullChargedCapacity` / 两者比值 |
| 循环次数 | `BATTERY_INFORMATION.CycleCount`（本机 78，与 WMI 一致） |
| `BatteryPowerStatus` | `POWER_STATE.BATTERY_POWER_ONLINE` |
| `BatteryAbnormal` | 无电池→1、`FullCharged/Designed < 0.8`→2、`Rate` 异常→3 |

> 注意：本机 `Win32_Battery.FullChargeCapacity` 为空、`BatteryStaticData` 类不存在，**必须先 IOCTL 验证再落 UI**，否则会出现"设计容量 0"。

#### P0-② 高性能电源模式补齐

现状已能切计划，缺两块：

1. **overlay 语义**：调用 `PowerSetActiveOverlayScheme(GUID_BEST_PERFORMANCE)`，让 Win11 设置页的"电源模式"同步显示为"最佳性能"，避免两处状态打架。
2. **计划持久化**：官方是 `PowerDuplicateScheme(平衡)` → `PowerWriteFriendlyName("机械革命 高性能")` → 激活。可选实现，好处是重启/切计划后仍能识别自家计划（按 FriendlyName 匹配），坏处是会在用户机器上多出一个计划，需要提供 `POWER_PLAN_DELETE` 清理。

推荐先做 ①，② 作为可选。

#### P0-③ 深度睡眠映射

本机没有 S3、没有固件语义，官方 `DEEPSLEEP_ON {Secs}` 无法 1:1 复刻。可行的**近似**：

| 官方语义 | 本机近似实现 |
|---|---|
| 空闲 N 秒后进入深度睡眠 | `powercfg /setacvalueindex SCHEME_CURRENT SUB_SLEEP HIBERNATEIDLE <N>` + `/setactive` |
| 不改变用户可见的"睡眠"行为 | 只写 `HIBERNATEIDLE`，不动 `STANDBYIDLE` |
| 切换后需重启 | 本机可即时生效，**无需重启**（保留 UI 的重启提示会显得多余，可改为"立即生效"） |

若用户想要更接近"深度睡眠"的效果，可额外提供"合盖休眠"选项（`LIDACTION` 写 2=休眠）。

#### P1-④ 电池三档充电阈值（重点与难点）

**障碍**：本机 `\\.\ACPIDriver` 不存在，MIFS 无对应功能号。要写 EC 0x7B9/0x7D0 必须先解决 EC 访问通道。三条候选路径：

| 路径 | 可行性 | 说明 |
|---|---|---|
| A. 安装官方 `UWACPIDriver.sys` | ❌ | INF 只绑 `ACPI\INOU0000`，本机 ACPI 命名空间无此设备；强改 INF 绑 `PNP0C14\MIFS` 会与现 WMI provider 冲突 |
| B. WinRing0 端口 I/O（0x66/0x62） | ⚠️ 中高风险 | 本机已有 `WinRing0_1_2_0` 在跑，具备 `ReadIoPortByte/WriteIoPortByte` 能力。但 0x7B9/0x7D0 超出标准 EC 256 字节窗口，需要 **bank 切换**；bank 寄存器地址未知（项目里曾怀疑 0x1060，实测读写会与遥测 EC 读并发卡死 handler） |
| C. 静态逆出 bank 协议后实施 B | ✅ 推荐前置步骤 | 从 BIOS 镜像解出 DSDT/SSDT（UEFITool 提取 + `iasl -d`），搜索 `OperationRegion(ECOR, ...)` 与 0x7B9/0x7D0 附近的 `Field`/`Store`，即可确定 bank 机制与官方 EC 字段名 |

**建议流程**（每步都可回退）：

1. **静态**：解 BIOS → DSDT/SSDT → 找 EC OperationRegion 与 `BAT0`/`EC0` 设备下的充电阈值字段，确认 0x7B9 是否被固件真实实现、bank 怎么切。
2. **只读探测**：在**用户在场**时，用 WinRing0 按 DSDT 找到的 bank 序列读 0x7B9/0x7D0，看返回值是否落在 0-100 的合理区间。只读不写。
3. **写入验证**：写入一个明显但安全的值（如 80），观察 ①`powercfg /batteryreport` 的充电曲线 ②UI 电量是否停在 80% ③EC 回读是否稳定。
4. **封装**：成功后再接 `BatteryProtection/Control` 的 `PERFORMANCEDMODE/BALANCEDMODE/HEALTHYMODE`，映射到 100/80/60（或 DSDT 里读到的真实档位），并保留 `RECOVERY` 命令恢复出厂值。

**若第 1 步就发现 0x7B9 在 DSDT 里没有被任何方法引用** → 说明本机 EC 固件压根不支持充电阈值，应立即停止 P1-④，改为"UI 上明确标注本机不支持"（见 8.5 风险 3）。

#### P1-⑤ 关机 USB 给电

比 ④ 简单：目标是 `ADDR_TRIGGER_BYTE (0x767)` 的 bit4。它同样需要 EC 写通道，但**风险更低**（单 bit、可回读、误写只影响关机供电）。

实现要点：
- 写前先读回整字节，**只改 bit4**，其余位保持（RMW），避免误清 `WinLock/LightBar/FanBoost` 等共用位。
- 写后延时 ≥200 ms 再回读校验。
- 若与"摄像头电子快门"复用同一位（`E_Shutter_Trigger_Camera_On`），需在 UI 上提示"该开关与摄像头快门共用固件位，不同项目语义不同"。

### 8.4 风险与缓解

| # | 风险 | 影响 | 缓解 |
|---|---|---|---|
| 1 | **EC 写与 ACPI EC 驱动争用** | 系统卡顿、EC handler 挂死、需硬断电 | 所有 EC 写放独立线程 + 全局锁；写前 `Wait` STS.IBF/OBF 位并设超时；**绝不并发**遥测读；先只读后写 |
| 2 | **bank 切换错误** | 写到错误寄存器，可能改风扇/功耗墙 | 严格按 DSDT 序列；每次写前读回原值确认落在预期地址；先在一项（USB 充电）上验证 |
| 3 | 固件不支持却强写 | 无效或异常状态 | 先做"只读探测"；读回值不在合理域就判定不支持并禁用 UI 项 |
| 4 | 三档阈值数值猜错 | 用户以为在保护电池，实际没变 | 阈值必须从 EC 读回，禁止硬编码；UI 显示"当前上限 XX%"实时回读值 |
| 5 | 电池信息字段取不到 | 面板显示 0/空白 | IOCTL 失败回退 `GetSystemPowerStatus` + WMI；每个字段独立降级 |

| 7 | 深度睡眠语义误导 | 用户以为能 S3 深度待机 | UI 文案改为"空闲 N 秒后休眠"；避免复用官方"深度睡眠"字样 |
| 8 | 与官方 UI 抢控制权 | 两套服务同时写 EC | 保持"只有一个桥接"的架构；若装官方 GCUService 必须先停桥接 |

### 11.3 遗留问题

| # | 问题 | 影响 | 后续动作 |

| 1 | **放电续航未实测**：当前满电静置（Rate=0），只能验证 `-1` 分支 | `BatteryTime` 在放电时是否给出正确分钟数未验证 | 拔电使用 10 分钟后看电源页是否显示真实剩余分钟 |
