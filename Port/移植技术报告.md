# 移植技术报告 — 机械革命控制中心 5.56 → 蛟龙16 Pro 2023 (MRID6)

> 2026-09-26 移植完成并在本机实测通过。本文档供后续维护/二次开发参考。

## 1. 为什么官方 GX 包不能直接装

| 组件 | 官方 GX 包的做法 | 蛟龙16 Pro 2023 的现实 |
|---|---|---|
| 硬件访问 | `UWACPIDriver.sys` 绑定 ACPI 设备 `acpi\INOU0000`（Uniwill 专用） | 同方底盘，DSDT 中**无** INOU0000 |
| 机型逻辑 | `GCUService.exe`（.NET，混淆加密）内置 PH4x/PH6x 机型与 EC 表 | 不含 MRID6，寄存器映射不适用 |
| UI | `CCU.WinUI.msix`（WinUI3，未混淆） | **可直接复用** |

`INOU0000` 是 Uniwill 准系统的固件 ACPI 设备（Linux 内核 `uniwill-laptop` 驱动文档可查证）。

## 2. 蛟龙16 Pro 2023 的固件控制接口（本机实测验证）

`root\WMI` → 类 `MICommonInterface`，实例 `ACPI\PNP0C14\MIFS_0`，方法
`MiInterface(byte[32] InData) → byte[32] OutData`：

- `InData[1]` = 0xFA(GET) / 0xFB(SET)；`InData[3]` = 功能号；`InData[4..]` = 参数
- 功能号（来自第三方蛟龙控制中心反编译 + 实测）：

| fn | 名称 | 说明 |
|---|---|---|
| 8 | SystemPerMode | 0=均衡(游戏) 1=狂暴(性能) 2=办公(安静) |
| 9 | GPUMode | 0=混合 1=独显直连（v1 未接入） |
| 11/12 | FnLock / TPLock | |
| 13 | CPUGPUFanSpeed | 读双风扇转速：CPU=(b5<<8)+b4，GPU=(b7<<8)+b6 |
| 19 | SystemAcType | 电源状态 |
| 20/21 | MaxFanSpeedSwitch / MaxFanSpeed | 手动锁速开关 / 锁速值(%) |
| 22 | CPUThermometer | CPU 温度 (OutData[4]) |
| 23 | CPUPower | 子功能：[2,w]=SPL [3,w]=SPPT [4,t]=温度墙（单位 W/℃） |
| 16-18 | RGBKeyboard* | 键盘灯效（v1 未接入） |

旧第三方控制中心的 EC 直写路径（备用参考，v1 未用）：
WinRing0 + ITE 扩展寻址（端口 0x66/0x62，命令 0x2E），风扇占空比 EC RAM
`0xC83C/0xC83D`，手动模式位 `0xB20.1`。

## 3. 官方 UI 协议（反编译 CCUWinUI.dll 全量还原）

- 传输：MQTT `127.0.0.1:13688`，clientId `UWPClient_5`，
  user `UWPClient_User_5`，pass `UWPClient_Pwd888881772688_5`，
  cleanSession=false，keepalive=1s；订阅 QoS0，发布 QoS2。

- 核心业务 Topic：
  - `System/Control {System_ON|System_OFF}` — 遥测启停（5s 周期）
  - `System/CpuInfo|GpuInfo|FanInfo|DiskInfo|HardwareInfo|FanErrorInfo|BatteryProtection`
    注意 UI 显示 `CpuMaxFrequency` 时原样当"基准频率"、×4 当仪表值 → 服务发基准时钟即可。
  - `Fan/Control {Action}`：GETSTATUS / OPERATING_OFFICE|GAMING|TURBO|CUSTOM_MODE /

    SET_OPERATING_MODE_DETAIL（CpuAmdSPL/SPPT/FPPT/CpuAmdTccTarget 等）

  - `Fan/Table` = {Activated,Name,FanControlRespective,CpuTemp_DefaultMaxLevel,GpuTemp_DefaultMaxLevel,CPU:[{ID,UpT,DownT,Duty}],GPU:[…]}
  - `Setting/Control GETSTATUS` → `Setting/Status`（MySetting）+ `Settings/DeviceSwitchItemStatus`
    （注意 `TochpadEnable` 是源码原始拼写，少一个 u）
- UI 日志：`C:\ProgramData\CCU_Gallery`；桥接日志：`C:\ProgramData\JiaoLongCCUBridge`。

## 8. 重要事故记录：灯光页"闪退"的真正根因（cdb 转储分析）

2026-09-26 用户持续反馈"点击灯光闪退"。开启 WER LocalDumps（DumpType=2）+ cdb 分析转储后定位：

- 崩溃异常：`System.IO.FileNotFoundException`（HRESULT 0x80070002）——出现在 HomePage 构造函数（XAML ActivateInstance）、`Program.DecideRedirection()`（Main 入口）等随机位置，与点击哪个页面无关；
- 决定性证据：转储中进程模块路径为 `C:\Program Files\WindowsApps\CCU.WinUI_5.56.60.34_x64__fkb4sgs34zp4p\...`，发布者哈希与官方包（`__wrbgcf7aesyd8`，Publisher CN=AISTONE）不同——实际是 Publisher `CN=JiaoLongCCU-Port` 的重签名包（另一会话为删除应用商店模块所做的重打包）；
- 结论：该重打包 msix 的文件清单与实际内容不一致，运行时随机 FileNotFound 闪退（主页进不去、点任何页面都可能崩）；
- 修复：移除该包 → 装回原版 PreinstallKit 的 `CCU.WinUI.msix`（CN=AISTONE，572 文件，校验完整）→ payload 同步替换回原版；恢复后应用正常启动，自动点击灯光页存活，无新转储。

**教训：重签名/删模块必须保证 AppxBlockMap 与文件实际内容完全一致（用 makeappix pack 而非手工改 zip），否则必然随机闪退。交付包 payload/CCU.WinUI.msix 已固定为官方原始包。**

## 12. 电池页"电源设置/电池设置没效果"根因与修复（2026-09-27，已修复）

电池（电源管理）页两块控件的原始实现只做了"应答"，没有真实后端，且存在回显覆盖问题：

1. **电池保护模式（平衡/工作站/长效）选了又弹回**：`HandleBatteryControlAsync` 只回显一次，
   而遥测每 3 秒的 `System/BatteryProtection` 用硬编码 `HealthProtectionStatus=1` 覆盖 →
   任何选择约 3 秒内自动跳回"平衡模式"。
2. **高性能电源模式开关无任何作用**：本机注册表 `HighPerformancePowerModeSupport=0`，但 UI 的
   `RefreshItemsSupport` 写的是 `!Convert.ToBoolean(值)`（DWORD 0 → false → 取反为 true），开关反而
   可见；桥接侧该动作落入 default 分支仅记日志，`Setting/Status` 也不回发
   `HighPerformancePowerModeSwitch`，重启 UI 后开关状态丢失。
3. USB 充电 / 深度睡眠 / 来电自动开机 / 电池 Logo：同样仅 acknowledgment，无状态回发。

修复（对照官方 GCUService 反编译：`BatteryProtection2` 用 EC 写充电阈值，`PowerPlanSetting`
用 powercfg 切电源计划）：

- **电池保护模式**：本机固件 MIFS 无充电阈值功能号（fn0-7/24-40 全空，见 §6），官方 EC 阈值寄存器
  在同方底盘无公开映射，不宜盲写 → 按状态记忆处理：选择持久化到 `state.json`（`BatteryHealthMode`），
  GET/遥测统一回发持久值，选择不再弹回。真实充电阈值仍不可用（固件限制）。
- **高性能电源模式（真实生效）**：`WinPower` 新增 powrprof P/Invoke
  （`PowerReadActiveScheme`/`PowerSetActiveScheme`，Session 0 可用）。
  ON → 激活 Windows 高性能计划 `8c5e7fda-e8bf-4a96-9a85-a6e23a8c635c`；
  OFF → 恢复平衡计划 `381b4222-f694-41f0-9685-ff5bb260df2e`；
  状态存 `state.json`（`HighPerformancePowerMode`），服务启动时若为 ON 自动重新激活高性能计划
  （与官方 Init→LoadRegistry→SetPowerPlanMode 行为一致）。
- **USB 充电/深度睡眠/AC 恢复/电池 Logo**：BIOS/固件级功能，本机无接口，按"状态记忆类"处理
  （`UsbChargerState`/`DeepSleepState`/`DeepSleepSeconds`/`AcRecoveryState`/`BatteryLogoState`）。
- **`Setting/Status` 补发字段**：`UsbCharger`、`HighPerformancePowerModeSwitch`、`DeepSleepSwitch`、
  `DeepSleepTime`、`AcRecoverySwitch_Status`、`BatteryLogo_Status`（UI 按 `Contains("OFF")` 判开关）。

端到端实测（TestClient batterytest/batterytest2，4 项全 PASS）：HEALTHYMODE 后 GET 恒为 2 不弹回；
高性能开关 OFF→powercfg 显示"平衡"、ON→"高性能"，`Setting/Status` 同步回发。
注意：本机开机默认在"高性能"计划，UI 里关掉该开关会切到"平衡"，属预期行为。
TestClient 已改为通用联调驱动：`TestClient send <topic> <json> | batterytest | batterytest2`。

## 13. 主页三连击自定义"没效果"根因链与补丁重打（2026-09-27）

## 14. 主页"自定义模式没有效果"根因与修复（2026-09-27）

### 14.1 官方交互链路（反编译还原）
主页模式选择的四个 radio：办公/均衡/狂暴直接发 `Fan/Control OPERATING_*_MODE`；
**自定义 radio 只发 `NavigationToSubPageMessage(CustomModeSettingPage)`（打开自定义设置页）**，
不直接切模式。模式真正切入自定义靠设置页里的两个动作：
- 选择 Profile（`CustomModeProfileSetCommand` → `OPERATING_CUSTOM_MODE`，受
  `_isLoadCompleted`/`_manualResetProfileIndex` 门控）；
- 改功耗墙/超频滑块（`SET_OPERATING_MODE_DETAIL`，仅自定义设置页发出）或应用风扇曲线
  （`SET_FAN_SPEED_CURVE_SETTING`）。

### 14.2 两个根因
1. **桥接把 Fan/Status 的 `PowerMode` 错误镜像成性能模式**。官方语义（实测校准，
   与直觉相反）：**"1"=电源适配器，"0"=使用电池**——自定义设置页在 "0" 时显示
   “在电池模式下，自定义设置已被禁用”。用户在办公模式（桥接发 "0"）打开设置页必然触发；
   注意镜像值 1/2（均衡/狂暴）恰好不触发，更具迷惑性。第一次修复曾把方向弄反
   （AC 发 "0"），靠用户复测的截图纠正。
2. **桥接未实现"改设置即切入自定义"**：`SET_OPERATING_MODE_DETAIL` /
   `SET_FAN_SPEED_CURVE_SETTING` 只应用数值不切模式，且单 Profile 场景下下拉框没有
   变更事件可发 `OPERATING_CUSTOM_MODE`，自定义模式永远无法激活。

### 14.3 修复（桥接三处，重发布部署）
- `SendFanStatusAsync`：`PowerMode` = 真实电源状态（`SafeIsAc()` → AC="0"/电池="1"）；
- `HandleModeDetailAsync` / `HandleSetCurveAsync`：应用数值后调用
  `ActivateCustomMode()`（OperatingMode=3、CustomLoopActive=true、解除强冷锁、
  EC 手动锁速交给曲线环、启动自定义曲线控制环），与官方服务语义一致。
- 部署：`dotnet publish -r win-x64 --self-contained -p:PublishSingleFile=true`
  → 停服务 → 覆盖 `C:\Program Files\JiaoLongCCUBridge\JiaoLongCCUBridge.exe`
  → 起服务（dist payload 同步更新）。

### 14.4 追加根因：注册表缺 `IsAMDPlatform`，Fan/Status 缺滑块初始化字段
用户复测“CPU/显卡/风扇调整都没有效果”后的第三层根因：
- 自定义设置页的 VM 初始化滑块时，**AMD 分支以注册表
  `ItemSupport\IsAMDPlatform=1` 为前提**（反编译 CustomSettingPageViewModel
  `.ctor→RefreshItemSupport` 读该键；Fan/Status 处理器里 `if (IsAMDPlatform)` 才
  把 `CPU_AmdSPL/SPPT/FPPT/Cpu_AmdTccTarget/CPU_TccOffsetMaximum` 灌入滑块属性）。
  安装脚本与 RegistrySetup 均未写该键 → 整块跳过 → 滑块全 0、形同禁用。
- Fan/Status 还缺 UI 初始化要读的字段：`CPU_PL1Maximum/Minimum`、`CPU_PL2Maximum/
  Minimum`、`CPU_PL4Maximum/Minimum`（Intel 语义，AMD 上仅防 0 崩）、
  `CPU_TccOffsetMaximum`（AMD 路径 = 温度墙滑块上限，缺失则温度墙滑块上限 0）、
  `CPU_TccOffsetSwitch`（温度墙开关回显，桥接现于 SET_OPERATING_MODE_DETAIL 里
  跟踪并回发）。已全部补齐（PL 系列给 120/35、140/35、160/35 防御值，TccMax=95=TjMax）。
- 风扇曲线环（FanController，2s 周期 EC 直写 0xC83C/0xC83D）异常全部静默吞掉，
  无从判断是否在跑：已加周期日志（每 ~16s：cpu/gpu 温度、双风扇 duty、EC 可用性）。
- `CpuTccOffsetSwitch`（开启 CPU 温度墙开关）此前无处理：现在跟踪状态并回显，
  温度墙数值随 `CpuAmdTccTarget` 消息应用（fn23 子功能 4）。

### 17.4 两条铁律（本轮用无数次崩溃换来的）

1. **危险引用必须隔离在独立小方法，且 try/catch 要包在调用点**——JIT 失败发生在
   调用边界，方法内部的 try/catch 救不了自己（ToggleRow v3→v4 的教训）。
2. **降级路径和富控件路径不能在同方法**——否则富控件的缺失引用会拖垮降级代码的 JIT。

### 17.5 交互妥协

Slider/ToggleSwitch/ComboBox 全灭 → 富控件梦碎，全部降级为：
开关=点击 TextBlock 切换；枚举=点击循环；数值=−/+ 步进 TextBlock。
功能完整、零裁剪风险，但形态是「点击/步进」而非「滑杆」。频率曲线用
Path+LineSegment 真实绘制（官方 LineChart 同款画法）。
